## What this system is

A single-tenant business automation platform built for one real-estate agent (Marco Puga). It runs the full funnel: Instagram/ManyChat DMs and SMS in, an AI qualification pipeline, a Brivity-backed CRM, transaction and finance tracking, email marketing, lead-nurture and reporting agents, plus a short-form content pipeline that turns long video into published vertical clips. On top of it sits "Harvey," an operator-facing AI assistant with persistent memory that can read and act on the whole business state.

It deploys as one Docker image to Fly.io (app `marco-90-automation`, region `dfw`, 4 GB `performance-2x`, `/data` volume). Supervisord runs three processes in that image: the Node server on :3000, the OpenShorts Python video sidecar on :8000, and a CapCutAPI draft generator on :9001. Pushes to `main` (or `master`) trigger GitHub Actions, which builds with a buildx layer cache, pushes to `registry.fly.io`, and runs `flyctl deploy --image`.

## Architecture

- **`src/server.ts`** — one monolithic Express app (~10.5k lines, ~395 routes registered directly on `app`, no Routers). Also hosts the WebSocket upgrade router (ElevenLabs STT → Deepgram fallback → Hull `/ws`) and an OpenAI-compatible `/v1/chat` surface used by the WhatsApp gateway.
- **`src/core/`** — persistence + domain layer. ~12 `better-sqlite3` stores, each owning its own file under `/data` (`content.db`, `social.db`, `transactions.db`, `finance.db`, `email.db`, `auth.db`, `ads.db`, `sms.db`, `leadscores.db`, `reporting.db`, `crm-automation.db`, `voice-clone.db`, `outreach.db`, `content-planner.db`) plus ~11 JSON stores (`local-dashboard-db.json` is the main app DB: leads, conversations, tasks, dashboard snapshot). `types.ts` holds shared types and the role/permission model.
- **`src/agents/`** — 22 scheduled/autonomous agent families: `contentManager` (largest — ingest → clip → enhance → publish, with a Claude-driven `brain/` strategy loop), `emailMarketing`, `finance`, `reporting`, `leadNurture`, `transactionFlows`, `leadScoring`, `socialMedia`, `voiceClone`, escalations, reminders, and re-engagement.
- **`src/harvey/`** — the operator AI: `perception` (fresh business snapshot) → `judgment` (focus areas/directives) → `communication` (Sonnet operator voice), with Anthropic tool definitions in `tools.ts` and persistent episodic/semantic memory in `harvey-memory.db`.
- **`src/hull/`** — the general agent runtime under Harvey ("Aethon hull"): agent loop, model routing, graph memory (`aethon-memory.db`), voice STT/TTS, WebSocket transport.
- **`src/app/` + `src/modules/`** — the DM request path: webhook intake → funnel state → numbered pipeline steps (01–12) → Claude reply.
- **`src/integrations/`** — thin per-vendor clients: Brivity, Twilio, Sinch, Apify (TikTok), Gmail/Google Drive, ManyChat, upload-post, ElevenLabs, Anthropic, OpenShorts, Forewarn.
- **`public/`** — ~20 standalone HTML pages, no build step and no framework. `shell.html` is the app shell that iframes the rest; `crm-brivity.html` is the Brivity-replica CRM (the centerpiece), alongside `jarvis.html` (Harvey), `social.html` (Content Manager), `content-planner.html` (the editorial calendar — the plan, as distinct from the Content Manager's record of what was filmed), `dashboard.html`, `ads.html`, `finance.html`, `reporting.html`, and others.
- **`services/openshorts/`** — Python/FastAPI video sidecar. Upstream `mutonby/openshorts` cloned at build, with Marco-specific `*_marco.py` modules layered on: transcription, LLM viral-moment detection, gaze/take analysis, auto-reframe, burned ASS captions, emoji overlays, dead-air removal. Concurrency- and memory-guarded for the 4 GB VM.
- **`vendor/openreel`** — vendored MIT browser clip editor served same-origin at `/editor`, patched to load a clip by `?clip=<id>&token=`.
- **Auth (built, not enforced)** — session cookie `mp_sid` + scrypt passwords + `sessions`/`login_history`/`audit_log` in `auth.db`, gated behind the `SITE_LOGIN_ENABLED` env kill switch. Legacy API auth is `DASHBOARD_TOKEN`. See Known gaps.

(Later the same day it became a top-level sidebar tab and the Content Manager's own Calendar tab was removed — see the entry above.)

  **Time is the part that had to be got right, and it is where the naive version is wrong twice a year.** Every scheduled instant is stored as **UTC ISO 8601**, alongside `authored_tz` — the zone the human typed the time in — because "move this three days later, same time" only means something against a wall clock, and across a DST changeover the wall clock and the instant disagree (that move is **71 hours, not 72**, and the suite asserts exactly that). `zonedTime.ts` does the arithmetic with **`Intl.DateTimeFormat` and the runtime's own ICU database** — no new dependency, which the fast overlay deploy path could not have installed anyway — including the inverse direction (wall clock → instant) via a two-pass fixpoint. The two DST discontinuities are **reported, not guessed**: 2:30 AM on a spring-forward date *does not exist* (stored at 3:30, flagged `nonexistent`) and 1:30 AM on a fall-back date *happens twice* (stored as the first occurrence, flagged `ambiguous`), each surfaced as a badge on the card and a line in the panel. Cards show **both zones** — creator and target audience — with a `+1d`/`-1d` badge when they fall on different days, and the **Grid Timezone Anchor** genuinely re-sorts a card into a different day cell rather than relabelling it (a 11:30 PM Chicago post sits on the 19th when the grid is anchored to Manila).

  **Two drag modes, one global setting, three synchronised controls** (header switch, floating bubble, and holding `Shift` to use the other one for a single drag). **Domino** ripples: dropping a card `n` days later moves *every* scheduled post from its original date onward by the same `n`, each keeping its own wall clock; a **hover preview** highlights the affected cells and names the count **before anything is written**, and the whole ripple applies in one transaction. **Direct** expands the cell after a 200ms dwell into an hourly timeline with a 2px insertion line and moves **only** the dragged card — a Direct drag that rippled anything would be the same bug in reverse, so both directions are asserted.

  **Scratchpad backlog** is `scheduled_at_utc IS NULL` — one table, not a second store, which is what makes drag-to-schedule and reverse-drag-to-unschedule cheap and lossless (**unscheduling moves an item, it never deletes one**; every field survives the round trip). List and Kanban views over Brainstorm → Drafting → Ready to Schedule, quick capture with auto-focus, search, and a bottom-sheet layout on a phone. **Assignment** reads the real CRM directory — `teamRoster` for accent colours and roles, the `users.ts` table for who has been offboarded, merged by name so an **inactive member is still shown on the content they own, flagged `(Inactive)`, rather than silently vanishing**. Assigning someone raises a **real notification on their Task Command board**, not just a log row. Cards carry 20×20 avatar chips with a 2px accent ring, stacked at −6px with a `+N` counter, and the header's team filter **dims** the rest to 30% rather than hiding them. The ten-colour palette computes black-or-white type from **WCAG relative luminance** server-side and applies the identical rule in the browser, so every swatch clears 4.5:1 against its own label. Panel edits **auto-save on a 500ms debounce**; cells cap at three cards with a `+N more`; an empty day offers to create the first item *for that date*.

  Routes: `GET /api/planner/bootstrap|items|backlog|settings|activity`, `POST /api/planner/items`, `PATCH|DELETE /api/planner/items/:id`, `POST /api/planner/items/:id/unschedule`, `POST /api/planner/reschedule(+/preview)`, `PUT /api/planner/settings`, `POST /api/planner/hook-assist`. **Honest about what is not wired:** hook assist is a real Anthropic call and returns a plain 503 saying the key is unset rather than a canned "suggestion"; the media drive field is a link you paste, not a Drive browser; and **nothing on this page publishes anything** — UTC storage is there so an auto-publish integration *can* be built on it later, but today the planner plans and the Content Manager publishes. Verified **99/99** (`verify-content-planner.mjs`): DST arithmetic against real IANA rules, domino vs direct in both directions, preview writing nothing, and a real Chromium driving the page — including synthetic HTML5 drag events through the actual handlers, measured chip geometry, and the debounce proven by asserting the server has *not* been hit 150ms in and *has* been 900ms in.

Both run off the **30,182-listing SimplyRETS mirror**, send over SMTP, and log what the contact did with the email — which is the signal the whole feature exists to produce. **The design was set by measuring the feed, not by copying Brivity's form.** Three findings changed what got built: (1) **every listing has `geo.lat === null`**, so a map-drawn polygon cannot be evaluated against anything — no map-draw control is offered, and area is expressed as places (city / postal / county / school district / subdivision), which the feed does populate; (2) **SABOR publishes no financing terms**, so Brivity's Financial Options group (FHA / VA / USDA / Texas Vet / seller carry) is absent rather than rendered and silently ignored; (3) the mirror holds **Active and Pending only, no solds**, so reports are built on what is on the market now and say so. `mlsFacets.ts` computes the board's real vocabulary — every city, postal code, school district, property type and feature, with counts — so the builders **render only filters the data can answer**, and name in the UI the fields they cannot, with the reason. **Smart Radius, honestly re-implemented:** Brivity widens a geographic radius until the comp set clears 15; with no coordinates that is impossible, so `marketReport.ts` climbs a place ladder (postal → city → county → whole board) with the identical floor of 15, and the report **states which rung it landed on** ("Widened from 78245 (0 listings) to San Antonio to reach at least 15 comparables") — a silent radius does not tell the agent how local the number is. **THE VALUE ESTIMATE IS NOT AN AVM and never pretends to be:** it is the median price-per-square-foot of the comp set × the home's own square footage, with a low/high band from the quartiles — so **with no square footage on file there is NO number at all**, just a line saying what is missing. - [2026-08-13] — **Quo sync was silently losing two thirds of the text history to rate limiting** (`src/integrations/quo/index.ts`, `src/core/quoSync.ts`, `scripts/verify-quo-sms.mjs`). The first production sweep reported **8 threads / 14 messages**; a local run of the same code had reported 16/23, and the run before that 16/24. **Numbers that move between identical runs are the tell** — the sync was swallowing failures, and the count was whatever happened to get through. Quo publishes its policy on every response (`ratelimit-policy: "per-second"; q=10; w=1`, with `r` remaining and `t` to reset): **ten requests per second.** A full sweep is one request per conversation across 286 conversations, so the limit is not a corner case, it is the normal path — and the client had neither a limiter nor a retry, while the sync's `catch { return; }` turned every 429 into "that thread has no texts". **Worse than the loss was that it was permanent:** the partial pass was recorded as a completed full sweep, and incremental runs only revisit conversations that MOVED, so the ~40 missing threads would never have come back on their own. Three fixes. (1) **Requests are spaced, not counted** — a counting window, even a sliding one, lets the whole quota leave in a burst, and the gap between taking a slot and the request landing is not constant (~75ms on a cold socket, ~5ms warm); measured against a stub, a limiter "capped at 8/sec" delivered **16 in one second** purely from that jitter, so slots are now issued at a fixed interval and a 429 backs off *every* pending request, not just the one that got refused. (2) Retries honour `Retry-After`/`t` for 429 and 5xx, four attempts; a non-429 4xx still fails immediately, since it will fail identically on a retry. (3) **Failures are counted and reported** (`threadsFailed` on the sync result, logged), and **a pass with any failure is never recorded as a full sweep**, so the next run retries instead of assuming those conversations are call-only. A `FULL_SYNC_VERSION` stamp makes a mirror built by an older, wronger sweep re-sweep itself once on the next boot, so production repairs itself with no manual step. Result on the live account, now reproducible run to run: **48 threads / 81 messages, 0 failed, 38s** — up from 8/14. `QUO_API_BASE` was added purely so the suite can point the client at a stub returning real 429s; the retry path cannot be proven against the live API without deliberately abusing Marco's account. Verified **24/24**. **Also disproven while measuring:** the earlier note that Quo had never sent an outbound text — the fuller mirror contains outgoing messages with status `delivered`, so A2P/carrier registration on the line is working, not merely untested.

- [2026-08-13] — **Quo SMS is live in the CRM: real text threads on the Message Center's SMS tab, and a composer that actually sends** (`src/integrations/quo/index.ts`, `src/core/quoStore.ts`, `src/core/quoSync.ts` (all new), `src/server.ts`, `public/crm-brivity.html`, `scripts/verify-quo-sms.mjs` (new)). Quo is the phone system behind Marco's business line, **(737) 283-4703** (`PNo1mCxawI`, owner `pmarcopuga@gmail.com`). The SMS tab existed but was permanently greyed out because nothing ever put a conversation on the `sms` channel, and — the part that mattered more — **the thread composer's send only pushed a bubble into local state; it never sent a text to anybody.** Both halves are real now. **Two facts about the account dictated the design, and both were measured against the live workspace before any code was written.** First, `Authorization` takes the API key **raw, with no `Bearer` prefix** (the bearer form 401s). Second, the workspace holds **286 conversations that are overwhelmingly CALLS, not texts**, and nothing on a conversation row distinguishes them — so a sync that assumed "conversation = text thread" would have filled the CRM with hundreds of empty call logs posing as SMS. `GET /v1/messages` also *requires* both `phoneNumberId` and `participants` (repeated single-valued `participants=`; `participants[]=` is rejected as "Expected array"), so there is no inbox call and a full pass is necessarily conversations-first, then messages per thread — hence a full sweep on first connect, incremental by `updatedAt` after that, concurrency 4, and call-only threads skipped. A real full pass reads 286 conversations down to **16 text threads / 23 messages**. **`quo.db` is keyed by PHONE, never by lead, deliberately** — Quo's book contains carriers, spam and one-off numbers, and writing them into the lead store would not merely be untidy: `createLead()` fires real outbound automations (a Twilio text to Marco and Carlos, a marketing auto-reply, a drip enrolment). ## Known gaps / open issues

- **Gmail OAuth refresh token is dead — but outbound email no longer depends on it.** As of 2026-08-11 the system prefers **SMTP with an app password** (`GMAIL_SMTP_USER` + `GMAIL_SMTP_APP_PASSWORD`), which does not expire weekly; OAuth is the fallback and is still what READS the inbox. The original finding, still accurate about OAuth: Confirmed live 2026-07-28: `/api/email/connection-status` returns `invalid_grant: Bad Request`. `invalid_grant` (not `invalid_client`) is the key detail — **the Fly secrets are all present and correct** (`GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` all show Deployed; bad app credentials would report `invalid_client`). Google has invalidated the refresh token itself. This kills **every** outbound path — drip campaigns, digests, and task-assignment emails. It is not caused by any recent code change. This is the second occurrence (the previous token died 2026-06-22), and a *recurring* `invalid_grant` on an otherwise untouched token is the signature of an OAuth consent screen still in **"Testing"** publishing status, where Google expires refresh tokens after 7 days. **Relinking restores sending but will die again in a week unless the consent screen is published to "In production"** in Google Cloud Console. Relink (no deploy, no secret rotation): open `https://marco-90-automation.fly.dev/api/email/gmail-oauth/start` signed in as Marco; the fresh token is written to the email DB on `/data`, which `getConfig()` prefers over the env var — note this makes `tokenSource` flip `env` → `db`, so the stale `GMAIL_REFRESH_TOKEN` secret stops being consulted.
- **The CRM stage field has never actually been used.** All 746 production leads are `crmStage: "new"` (confirmed 2026-07-27 via the tracker backfill dry run). Every stage-derived view — funnel counts, stage filters, the tracker migration — therefore has no real history to work from, and the tracker's pipelines will be populated by hand or by automation going forward, not by migration.
- **The CRM shows 230 of 746 leads.** `getDashboardSnapshot()` does `if (!hasPhone) continue`, so the ~511 Instagram/TikTok DM contacts who never gave a phone number are in the lead store but invisible in the CRM UI (only 4 leads have an email). This is deliberate, but it means "how many leads do we have" has two different right answers, and the tracker backfill currently targets the 746, not the 230.
- **The tracker holds 1,219 records and every one of them is Unstaged.** Neither the CRM nor Brivity has ever used its stage field (2,591 of 2,595 Brivity contacts are stage "new"), so there was no pipeline history to import and stages must be set by hand or by future automation. 747 of the 1,219 are contactable (742 phone, 448 email); the other 472 are Instagram/TikTok handles with no phone or email, hidden behind the tracker's "Contactable only" filter.
- **Nothing syncs the CRM and the tracker after the import.** `leadId` is set on backfilled records, but no code updates a tracker record when its lead changes (or the reverse), so the two drift from here.
- **Tracker→task links are per-item and manual.** Pushing a checklist item to the Task Manager is an explicit action; nothing auto-creates tasks from a stage change or a new checklist item. Task→tracker completion is resolved at read time, so it is correct whenever the tracker is loaded but there is no push notification to an already-open tracker tab (hit Refresh).

- **Security — the app is currently unauthenticated.** `SITE_LOGIN_ENABLED` is off in production (owner's explicit decision: "keep it in the back end for now"), and `dashboardTokenOkIncoming()` returns `true` whenever `DASHBOARD_TOKEN` is unset. Re-enabling is a one-secret change, no code edits.
- **Default branch is wrong.** GitHub reports `master` as the default branch, but `master` is a stale, *unrelated* history (7 commits, last real change 2026-07-20) with no merge base against `main`. All 267+ commits of real work, and every deploy, live on `main`. This file is on `main`. Until the GitHub default is flipped to `main`, the Chronicler's nightly sweep will look at the wrong branch and miss this file.
- **`server.ts` is a 10.5k-line monolith** with ~395 routes on a single `app` and no Routers. It works, but every feature widens the same file; it is the main structural debt here.
- **Ad Manager is hidden and is reporting + local planner only.** Its shell tab is commented out (owner's request), though `/ads` and `/api/ads/*` still serve. There is no Meta Business/ad-account write access, so nothing in the app can create or edit a real campaign. Doing so needs a System User token, an ad account ID, and spend guardrails (budget caps, approval-before-live) that do not exist yet.

- **No test suite and no linter.** `npm run build` (tsc) is the only automated gate; verification is manual, usually a headless-browser pass before deploying.
