## What this system is

A single-tenant business automation platform built for one real-estate agent (Marco Puga). It runs the full funnel: Instagram/ManyChat DMs and SMS in, an AI qualification pipeline, a Brivity-backed CRM, transaction and finance tracking, email marketing, lead-nurture and reporting agents, plus a short-form content pipeline that turns long video into published vertical clips. On top of it sits "Harvey," an operator-facing AI assistant with persistent memory that can read and act on the whole business state.

It deploys as one Docker image to Fly.io (app `marco-90-automation`, region `dfw`, 4 GB `performance-2x`, `/data` volume). Supervisord runs three processes in that image: the Node server on :3000, the OpenShorts Python video sidecar on :8000, and a CapCutAPI draft generator on :9001. Pushes to `main` (or `master`) trigger GitHub Actions, which builds with a buildx layer cache, pushes to `registry.fly.io`, and runs `flyctl deploy --image`.

## Architecture

- **`src/server.ts`** — one monolithic Express app (~10.5k lines, ~395 routes registered directly on `app`, no Routers). Also hosts the WebSocket upgrade router (ElevenLabs STT → Deepgram fallback → Hull `/ws`) and an OpenAI-compatible `/v1/chat` surface used by the WhatsApp gateway.
- **`src/core/`** — persistence + domain layer. ~13 `better-sqlite3` stores, each owning its own file under `/data` (`content.db`, `social.db`, `transactions.db`, `finance.db`, `email.db`, `auth.db`, `ads.db`, `sms.db`, `leadscores.db`, `reporting.db`, `crm-automation.db`, `voice-clone.db`, `outreach.db`, `content-planner.db`, `contact-records.db`) plus ~11 JSON stores (`local-dashboard-db.json` is the main app DB: leads, conversations, tasks, dashboard snapshot). `types.ts` holds shared types and the role/permission model.
- **`src/agents/`** — 22 scheduled/autonomous agent families: `contentManager` (largest — ingest → clip → enhance → publish, with a Claude-driven `brain/` strategy loop), `emailMarketing`, `finance`, `reporting`, `leadNurture`, `transactionFlows`, `leadScoring`, `socialMedia`, `voiceClone`, escalations, reminders, and re-engagement.
- **`src/harvey/`** — the operator AI: `perception` (fresh business snapshot) → `judgment` (focus areas/directives) → `communication` (Sonnet operator voice), with Anthropic tool definitions in `tools.ts` and persistent episodic/semantic memory in `harvey-memory.db`.
- **`src/hull/`** — the general agent runtime under Harvey ("Aethon hull"): agent loop, model routing, graph memory (`aethon-memory.db`), voice STT/TTS, WebSocket transport.
- **`src/app/` + `src/modules/`** — the DM request path: webhook intake → funnel state → numbered pipeline steps (01–12) → Claude reply.
- **`src/integrations/`** — thin per-vendor clients: Brivity, Twilio, Sinch, Apify (TikTok), Gmail/Google Drive, ManyChat, upload-post, ElevenLabs, Anthropic, OpenShorts, Forewarn.
- **`public/`** — ~20 standalone HTML pages, no build step and no framework. `shell.html` is the app shell that iframes the rest; `crm-brivity.html` is the Brivity-replica CRM (the centerpiece), alongside `jarvis.html` (Harvey), `social.html` (Content Manager), `content-planner.html` (the editorial calendar — the plan, as distinct from the Content Manager's record of what was filmed; dates on it are literal, never timezone-converted), `dashboard.html`, `ads.html`, `finance.html`, `reporting.html`, and others.
- **`services/openshorts/`** — Python/FastAPI video sidecar. Upstream `mutonby/openshorts` cloned at build, with Marco-specific `*_marco.py` modules layered on: transcription, LLM viral-moment detection, gaze/take analysis, auto-reframe, burned ASS captions, emoji overlays, dead-air removal. Concurrency- and memory-guarded for the 4 GB VM.
- **`vendor/openreel`** — vendored MIT browser clip editor served same-origin at `/editor`, patched to load a clip by `?clip=<id>&token=`.
- **Auth (built, not enforced)** — session cookie `mp_sid` + scrypt passwords + `sessions`/`login_history`/`audit_log` in `auth.db`, gated behind the `SITE_LOGIN_ENABLED` env kill switch. Legacy API auth is `DASHBOARD_TOKEN`. See Known gaps.

## Recent changes (most recent first)

- [2026-08-31c] — **Brivity migration: the vocabulary mapping rewritten as explicit tables, because the old one mislabelled most of the database** (`src/core/brivityMapping.ts` NEW, `src/core/brivityPeople.ts`, `src/core/brivityImport.ts`, `scripts/verify-brivity-mapping.mjs` NEW).

  Before importing 2,855 Brivity contacts, the existing importer's field mapping was measured against the real export rather than trusted. It guessed with `includes()` substring tests, and on the live data it got the largest buckets wrong: `archived` (547) and `trash` (505) both collapsed to `dead` even though this CRM has `archived` and `trashed`; `past-client` (29), `active-client` (12) and `prospective-client` (1) matched `includes("client")` and became cold `watch` leads — a realtor's past clients are the referral list, and that filing loses the segment; `Attempted contact` (1,224), `Spoke with customer` (168) and `Met with customer` (2) all fell through to stage `new` because the stage mapper predates `CRM_LEAD_STAGES`, so 1,394 contacts lost their real stage; `seller/buyer` (202) became `seller`; and `n/a` (1,353) plus `tenant` (13) became `buyer`, inventing an intention for half the database. Brivity's five stages map one-to-one onto `CRM_LEAD_STAGES`, so none of that loss was necessary.

  Replaced with explicit tables (`BRIVITY_STATUS_MAP`, `BRIVITY_STAGE_MAP`, `BRIVITY_INTENT_MAP`, `INTENT_TAGS`, `recordKind`). Three principles: things this CRM's vocabulary cannot express are preserved as tags rather than crushed into the nearest status (client relationships, tenant/landlord); "Brivity did not say" stays `null` instead of defaulting to buyer; and an unrecognised value is **reported** in `unmapped`, never absorbed — if Brivity adds a status next month the import says so instead of quietly filing a thousand contacts under `nurture`, which is how the previous errors survived. An *empty* stage is deliberately not "unmapped" — 128 contacts have none, and saying nothing differs from saying something unrecognised.

  `recordKind` also separates the 125 `collaborator` and 3 `team` records (lenders, agents, staff) from the 2,727 real leads, so 128 non-leads stop landing on the call list. `BrivityPerson` was corrected to the API's actual 28 fields — notably **Brivity returns no timestamps at all**, so imported contacts cannot carry a real created/updated date, and `brivityLeadId`/`brivityUuid`/`brivityUrl` are now retained for traceability back to the old system. The create path previously hard-coded `crmStage: "new"` and dropped notes/address/tags; it now writes the mapped stage and carries them through. Address goes to the `address` field, not `criteria.location`.

  **Measured, not assumed.** Read-only probes established that `limit=5000` returns all 2,855 contacts in one call and that no pagination parameter (`page`/`offset`/`cursor`) has any effect; every non-`/api/people` route returns the identical `{"status":"406","error":"Not Acceptable"}` as a deliberately invented route, i.e. those endpoints do not exist rather than being broken. Agent identity comes from `agent_id`/`agent_uuid` on each person (2,854 of 2,855 on one agent). A dry run of the real archive through the new mapping produced 2,727 leads, 128 non-leads held back, and **0 unmapped values**.

  `scripts/verify-brivity-mapping.mjs` (30 checks) pins this with fixtures taken from the live export, each carrying its real contact count, so a regression reads as "29 contacts land in the wrong bucket" rather than something abstract.

  **Not yet run:** the import itself. This commit is the mapping and its proof only — `/api/brivity/import/apply` writes into the live CRM and is awaiting an explicit go-ahead.

  **Security:** the Brivity API key was shared in chat during this work and must be rotated.

- [2026-08-31b] — **Forensic UI/API audit: one layering scale, and five popups that were opening behind other things** (`public/crm-brivity.html`, `src/server.ts`, `scripts/audit-crm-modals.mjs` NEW, `scripts/audit-api-routes.mjs` NEW).

  **The reported symptom** — "I click Auto Plans on a lead profile and it pops up on the backend, you can't even see or access it" — was a stacking bug, and a whole class of them. z-indexes had been assigned ad hoc over time (80, 81, 90, 120, 9000), so anything opened from inside an `.oa-ov` modal (z-9000) rendered *underneath* it: `display:block`, correct rect, completely unreachable. Every test that asks "did the modal open?" passes on that. Only a hit test catches it.

  Five real defects, all confirmed by A/B against the unfixed file: the **Auto Plan editor**, **transaction modal** and **transaction detail** all opened behind any open modal; **every toast** fired from inside a modal painted behind it (so "Give the alert a name" and Quo's own send errors were invisible); and **anchored dropdown menus** (`.dd-menu`) opened behind modal content — the same complaint as the old "property type dropdown opens behind the popup".

  Fixed structurally rather than by bumping numbers again. `:root` now carries **one named layering scale** — `--z-chrome / --z-topbar / --z-drawer / --z-modal / --z-menu / --z-toast` — with menus and toasts in permanent lanes *above* modals, because a menu belongs to a control inside one and a toast is worthless painted behind the thing that produced it. Modal-over-modal is settled by open ORDER: `raiseOverlay()` assigns an incrementing z at open time, since a fixed number cannot express "whatever is newest". A `MutationObserver` on the overlay containers raises anything that becomes visible by some other path, so the rule does not depend on every future call site remembering it.

  **`scripts/audit-crm-modals.mjs`** (32 checks) is the instrument: it asks the question the operator is actually asking — *if I click the middle of this, do I hit it?* — and asserts that the overlay **just opened** is the topmost, not merely that something is. That distinction matters: a "topmost is clickable" rule passes happily on the broken code. It also walks all 14 rail views and all 6 lead-profile tabs for render errors. **`scripts/audit-api-routes.mjs`** exercises every GET route read from Express's own table: 250 routes, 210 OK, 39 legitimately asking for input, **0 handlers throwing**. It found one wrong status code — `/api/email/gmail/:messageId` answered **500** for "Gmail not configured", where every other integration here answers 503; a 500 sends whoever reads the network tab hunting for a bug in the handler. Now 503 with a hint.

  All 16 verify suites re-run green (1,231 checks).

- [2026-08-27] — **`GET /api/dm/inbound-report` — when did inbound DMs last actually arrive, per platform and per day** (`src/server.ts`, `scripts/verify-inbound-report.mjs` NEW).

  **The question no existing diagnostic answered.** "The TikTok automation stopped replying" has two causes that look identical from the inbox and need opposite fixes: messages are arriving and this server declines to answer them, or no message is arriving at all because the chain upstream — TikTok → ManyChat → the flow's External Request → `/webhook` — is broken. `/api/llm/health` and the intent-gate ledger both answer "what did we do with the message"; neither can answer "was there a message", and the ledger is in-memory so it cannot look back past a deploy. This one is computed from stored conversations, so it sees **backwards through a takedown that happened before anyone thought to instrument it** — the day-by-day histogram shows the cliff and its date.

  Counts inbound (`role: "user"`) messages only. Counting our own replies would show a dead channel as healthy, which is precisely the failure it exists to catch — that case is asserted. Returns per platform: last inbound timestamp, hours since, counts over 24h/7d/30d/window, distinct contacts, and a byDay histogram omitting silent days. Plus a plain-English verdict for the platform asked about, which distinguishes **stopped** from **never worked** — an operator told "stopped" about a channel that never ran would go looking in the wrong place.

  Counts and timestamps only: no message text, no names, no handles (asserted). Behind the site lock, because it describes real conversations. Covered by `scripts/verify-inbound-report.mjs` (23 checks).

- [2026-08-25b] — **Recurrence cadences that actually recur, the address discrepancy explained, and the listing-alert guard** (`src/core/types.ts`, `src/server.ts`, `public/crm-brivity.html`, `scripts/verify-crm-widgets.mjs`, `scripts/verify-outreach.mjs`).

  **The recurrence picker was offering cadences the engine silently ignored.** `spawnNextRecurrence` knew five intervals — daily, every 3 days, every 5 days, weekly, monthly — and returned `null` for anything else, meaning the successor task was **never created and nothing said so**. The operator's list adds Day of Week, Biweekly, Every 3 Months, Every 6 Months, Yearly and an open-ended "Every ___ Days", so the engine now advances a real date for every one of them. Two details that would otherwise be wrong: a monthly task due on the **31st clamps to the last day of the target month** instead of overflowing into the next one (`setUTCMonth` turns 31 Jan into 2 or 3 March), and a **day-of-week cadence moves a full week** rather than landing on the day just completed. `every_N_days` and `day_of_week_N` carry their number inside the interval string — validated by `isRecurringInterval`, which a plain Set cannot express — so the task store keeps one column instead of gaining two that one option each would ever fill. ## Known gaps / open issues

- **Gmail OAuth refresh token is dead — but outbound email no longer depends on it.** As of 2026-08-11 the system prefers **SMTP with an app password** (`GMAIL_SMTP_USER` + `GMAIL_SMTP_APP_PASSWORD`), which does not expire weekly; OAuth is the fallback and is still what READS the inbox. The original finding, still accurate about OAuth: Confirmed live 2026-07-28: `/api/email/connection-status` returns `invalid_grant: Bad Request`. `invalid_grant` (not `invalid_client`) is the key detail — **the Fly secrets are all present and correct** (`GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` all show Deployed; bad app credentials would report `invalid_client`). Google has invalidated the refresh token itself. This kills **every** outbound path — drip campaigns, digests, and task-assignment emails. It is not caused by any recent code change. This is the second occurrence (the previous token died 2026-06-22), and a *recurring* `invalid_grant` on an otherwise untouched token is the signature of an OAuth consent screen still in **"Testing"** publishing status, where Google expires refresh tokens after 7 days. **Relinking restores sending but will die again in a week unless the consent screen is published to "In production"** in Google Cloud Console. Relink (no deploy, no secret rotation): open `https://marco-90-automation.fly.dev/api/email/gmail-oauth/start` signed in as Marco; the fresh token is written to the email DB on `/data`, which `getConfig()` prefers over the env var — note this makes `tokenSource` flip `env` → `db`, so the stale `GMAIL_REFRESH_TOKEN` secret stops being consulted.
- **The CRM stage field has never actually been used.** All 746 production leads are `crmStage: "new"` (confirmed 2026-07-27 via the tracker backfill dry run). Every stage-derived view — funnel counts, stage filters, the tracker migration — therefore has no real history to work from, and the tracker's pipelines will be populated by hand or by automation going forward, not by migration.
- **The CRM shows 230 of 746 leads.** `getDashboardSnapshot()` does `if (!hasPhone) continue`, so the ~511 Instagram/TikTok DM contacts who never gave a phone number are in the lead store but invisible in the CRM UI (only 4 leads have an email). This is deliberate, but it means "how many leads do we have" has two different right answers, and the tracker backfill currently targets the 746, not the 230.
- **The tracker holds 1,219 records and every one of them is Unstaged.** Neither the CRM nor Brivity has ever used its stage field (2,591 of 2,595 Brivity contacts are stage "new"), so there was no pipeline history to import and stages must be set by hand or by future automation. 747 of the 1,219 are contactable (742 phone, 448 email); the other 472 are Instagram/TikTok handles with no phone or email, hidden behind the tracker's "Contactable only" filter.
- **Nothing syncs the CRM and the tracker after the import.** `leadId` is set on backfilled records, but no code updates a tracker record when its lead changes (or the reverse), so the two drift from here.
- **Tracker→task links are per-item and manual.** Pushing a checklist item to the Task Manager is an explicit action; nothing auto-creates tasks from a stage change or a new checklist item. Task→tracker completion is resolved at read time, so it is correct whenever the tracker is loaded but there is no push notification to an already-open tracker tab (hit Refresh).

- **Security — the app is password-locked as of 2026-08-22** (was completely open before that; see Recent changes). Two things are still owed: **(a) the third-party webhooks are unauthenticated by necessity** — `/webhook`, `/webhook/twilio`, `/sinch/inbound` and `/api/quo/webhook` accept anonymous POSTs, so anyone who learns those URLs can inject a fake inbound SMS or DM and create CRM activity. Twilio and Sinch both offer request signing and neither is verified here; that is the highest-value next fix. **(b) A scrypt hash for the initial admin is checked into `src/core/initialAdmin.ts`** because no Fly CLI access was available when the lock shipped. It is retired by the forced password change on first login, but it should be replaced by the `INITIAL_ADMIN_PASSWORD_HASH` secret and the marker bumped. Also worth setting: `DASHBOARD_TOKEN`, without which there is no machine credential at all — the Chrome browser-control extension (`/api/browser/*`) cannot authenticate and is dark until it is set.
- **Default branch is wrong.** GitHub reports `master` as the default branch, but `master` is a stale, *unrelated* history (7 commits, last real change 2026-07-20) with no merge base against `main`. All 267+ commits of real work, and every deploy, live on `main`. This file is on `main`. Until the GitHub default is flipped to `main`, the Chronicler's nightly sweep will look at the wrong branch and miss this file.
- **`server.ts` is a 10.5k-line monolith** with ~395 routes on a single `app` and no Routers. It works, but every feature widens the same file; it is the main structural debt here.
- **Ad Manager is hidden and is reporting + local planner only.** Its shell tab is commented out (owner's request), though `/ads` and `/api/ads/*` still serve. There is no Meta Business/ad-account write access, so nothing in the app can create or edit a real campaign. Doing so needs a System User token, an ad account ID, and spend guardrails (budget caps, approval-before-live) that do not exist yet.
- **The MLS feed has no solds and no coordinates, and the CMA is built around both facts.** `mlsFacets` counts Active and Pending only across ~32k rows, and `geo.lat` is null on every one of them. So CMA sold comparables come from Marco's own closed transactions or hand entry, off-market comps are hand entry only, and there is no map, no radius search and no distance sort anywhere in the wizard — the place ladder (postal → city → county → board) stands in for the radius. Adding a sold-status feed or a geocoding key would light all of that up without changing the UI's shape.
- **No website-visit tracking.** Several Brivity smart filters ("site visit today / this week / last 30 days") depend on it, so in both Leads and People they are listed but disabled with an explanatory toast rather than silently matching every row.
- **`AD_DASHBOARD_BASE_URL`** points at `https://marco-agents.fly.dev`, which is not currently reachable; the Ad Manager degrades to an honest "unreachable" badge.

- **No test suite and no linter.** `npm run build` (tsc) is the only automated gate; verification is manual, usually a headless-browser pass before deploying.
- **Several integrations are stubs** that throw or no-op: `integrations/manychat` (`sendDM`), `integrations/amazon`, `integrations/newhomebuddy`, `integrations/brivity/index.ts` (the real client is `integrations/brivity.ts`).

- Deploys cannot add npm dependencies via the fast overlay path; a new dependency requires a full image rebuild.
